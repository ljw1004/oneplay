# M17 plan: OnePlay Music on iOS

## Summary

Build an iPhone app under `music/ios/` that bundles OnePlay’s existing HTML, CSS, and compiled TypeScript in a `WKWebView`. Keep one library UI for the browser and iPhone. On iPhone, pressing Play hands Swift everything needed to play the session. The listener can lock the phone at track one, reach track ten, and reopen the library to find the correct row, footer, scrubber, and saved position.

**Start with the listening test.** Use the listener’s own CD-ripped MP3s. The known boundary is *Sgt. Pepper’s Lonely Hearts Club Band (Reprise)* into *A Day in the Life*. Use *The Wall* for several natural transitions, identifying continuous boundaries by listening to the local files first. Success on cellular means the transition sounds like a gapless-capable player playing those exact files locally. Honor encoder delay/padding information where present, preserve silence in the source, and leave crossfade and silence trimming off.

## Locked user decisions

- Deliver a signed Xcode installation on the listener’s own iPhone. The acceptance device is the physical iPhone. A simulator can exercise the UI and deterministic policy tests.
- Keep the existing library UI, OneDrive registration and cloud data. The native session must own continuous cellular playback while locked and play complete downloads offline. Judge the MP3 joins against the listener’s own files.
- When a playlist edit removes the playing occurrence, **finish the song, then play the next surviving track**. Apply this rule to both players as part of the shared extraction.
- **Cellular preload has a hard ceiling of 4 MB (4,000,000 bytes) for the single speculative successor.** Allow the prepared prefix of a FLAC recording to play while Swift obtains a fresh raw download URL, which can take 5–10 seconds. Retries, metadata ranges in the media object, discarded responses and cancellation overshoot all count. If the reference join cannot be achieved inside the cap, the prototype fails.
- Incomplete pins may resume when the app is reopened. Use foreground transfers and keep the playback session independent of pinning.
- Use a fresh GPT-6.2-Sol reviewer at High reasoning effort wherever the milestone process calls for Claude. The execution instructions above are reproduced verbatim.

**Prototype decision rule.** Keep a Release-like debug harness with a native monotonic timeline: preparation start/cancel, occurrence, URL lookup/renewal, first media byte, bytes by item, item-ready, transition, stall and route. Record an independent local reference first, then three cold runs of each chosen boundary on the same route. Disable pins and clear transient buffers for network runs. **Measuring speculative reads.** Compare successor body bytes at enqueue, the transition and after skip. Keep the accounting for the full speculative preparation, including cancelled work still draining, rereads of the same range and media headers/tails fetched from the file. Count every retry across URL renewal in the same budget. Use per-resource transport metrics or an independent recording transport if AVFoundation omits incremental bytes. Failed or unmeasurable runs cannot pass. The current audible item and intentional offline pins are separate transfers. Disable pins in this test. Accept the smallest tested buffer that reproduces the join within 4,000,000 received media-body bytes.

**Enforcing the cap.** Measure the preferred buffer required to cover the observed 5–10 second URL-renewal delay, starting with 12 seconds of playable audio as a trial. Prefer enough contiguous decodable audio at the start of the successor to cover that delay plus decoder startup, within the hard 4 MB cap. Report actual playable seconds for the test MP3s and FLAC; bytes buffered at the end of a file do not extend the runway at its start. Its setting cannot enforce a byte ceiling. For unpinned cellular playback use a native asset resource loader backed by metered URLSession reads unless the chosen transport exposes an equivalent enforceable cap. Keep both current and successor traffic under native ownership so a Wi-Fi-to-cellular change cannot leave an unmetered successor running. Use the same cap on both routes for speculative reads. Only one successor may fetch at a time. Reserve each range against the remaining allowance before issuing the request, and stop admitting new speculative requests when the allowance runs out. Replacement/cancellation drains the old request before starting another. Do not reset the budget on retry, a redundant preparation of the same upcoming occurrence, or a URL change. Release the speculative limit for *demand* reads when the item becomes current. A pinned file uses local bytes.

Give AVFoundation a private media scheme. Serve content-info and range requests from a per-recording sparse buffer that the player also consumes after promotion. Check offsets, object version and total length. Accept valid 206 responses matching the requested range. Accept a 200 for an entire file only when starting at zero and the identity and known complete length fit the remaining allowance. Reject ignored/nonmatching ranges or unbounded responses at the headers, count any bytes already transferred, and disable speculation on that source if it cannot be bounded. Never append a 200 body at a nonzero offset. Test 206, ignored ranges with a large 200 body, 416, cancellation, automatic retries and refreshed URLs. Reusing the prepared prefix on promotion must produce zero duplicate prefix fetches in the valid same-version range case. Capture actual transferred body bytes independently of the buffer high-water mark. If transport behavior or in-flight overshoot makes the hard ceiling unverifiable or exceeds it, that path fails. If a bounded path cannot meet the listening test, stop and report both results.

**Local decoder gate.** If the local decoder/scheduler adds a gap, try a continuous native PCM schedule with adjacent decoded regions and the files’ declared priming/padding. If that requires a new streaming decoder subsystem, or locked renewal fails with supported MSAL settings, stop at this gate and present the traces as a prerequisite milestone. Run all listening, lock, renewal, offline and transfer gates on the chosen shipping engine, including any PCM fallback. No shared-player rewrite rests on an unproven engine.

Prove queue changes at the audible boundary as part of this gate. With A audible and B enqueued, replace B with C, switch to One, select end-of-track, or expire the numeric timer just before A ends. Run the changes before and after the player reports a new current item. Remove only the queued successor while A is current. The adapter associates a preparation generation with each player item. Before acknowledging a change, invalidate old preparation, compare actual item identity before/after the queue operation and reconcile the result. AVFoundation can promote B independently of the app executor. If B has already taken over, apply the edit to B as the current song and report that outcome. Compare recorded audio and event order on both sides of the boundary; `currentItem` by itself cannot prove what the listener heard. Once a stop policy takes effect no successor audio should leak. Reproduce with the UI detached, including a lock-screen pause, and record the audio along with the events. If a command acknowledged while A is still current permits obsolete B to sound, use the scheduling fallback above or stop at the prototype gate.
