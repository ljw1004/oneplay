# Native audio fetching and cache policy

The progressive reader shipped in iOS build 15. Build 16 added warm seeks and the Debug cache display. Build 17 extends the Wi-Fi window from the current recording into the next one. Build 18 reuses the signed CDN URL for the recording until the CDN rejects it. Build 21 resolves the immediate successor at the start of playback and batches a metered scrub’s missing bytes. Audio fetching has three separate budgets: retained compressed bytes, network read-ahead for the current track, and speculative traffic for the next track. Browser playback continues to use the HTML audio element. [Browser comparison and earlier measurements](../../experiments/ios-playback/Evidence/phase5/BUFFERING.md)

## What stays in memory

- One `MediaPool` belongs to the signed-in player and survives changing tracks, reopening a decoder to seek, and replacing the library web view. The pool holds at most **40,000,000 bytes** of compressed audio. Its independent entry limit is 610 blocks, which bounds bookkeeping even for very short recordings. PCM, URLSession buffers, partial incoming blocks and bytes currently held by a reader have separate lifetimes and add to process memory.
- A dictionary entry is keyed by **drive ID, item ID, Graph eTag, file size and aligned byte offset**. Each entry holds immutable data and a last-use counter. Successful reads and insertions advance the counter. Inserting at capacity evicts the least recently used entry, scanning at most 610 entries. The block size is 65,536 bytes, except at EOF. The cache can hold disconnected regions and can reuse a recording reached through a different library path.
- The signed-in account keeps the 16 most recently opened OneDrive locations in memory, keyed by drive and item ID. Each Graph response binds the signed URL to its eTag and file size. An active decoder also holds its location. A seek, replay, Previous, Next or new preparation can reuse the same location, including for missing audio ranges. Sign-out clears these locations and the audio pool. A memory warning releases the retained audio blocks.
- A cached range is readable during URL renewal. If the CDN rejects a request, the next missing range needs a replacement URL. Matching Graph version and size allow the decoder to continue at that offset. A changed recording stops the old decoder and discards its cached bytes. A confirmed Graph denial discards the item.
- There is no fixed backward/forward split. Recently played bytes from an earlier song can survive while the next song plays. Eviction, process termination or account cleanup can make a revisit cold. The transient pool creates neither a durable download nor an offline badge.

## What goes over the network

| Situation | Current rule |
| --- | --- |
| Unmetered Wi-Fi | Aim for **6,000,000 compressed bytes ahead of the audible playhead** across the current song and its immediate successor. Check at decode boundaries with at least three seconds of PCM queued and playback running. Estimate the current byte position from elapsed frames, duration and file size. Admit the current window first. The immediate successor gets at least a 256 KiB opening allowance, even while more than 6 MB of the current song remains. In automatic modes its allowance grows as the window crosses EOF. No third song participates. |
| Cellular, hotspot, Low Data Mode, unknown or other route | A demand miss opens up to **256 KiB** during ordinary decoding. Once the current song is playing with at least three seconds of queued PCM, aim **45 seconds beyond the decoded position**. Apple's cached-header time-to-byte estimate handles variable bitrate. File size and duration supply the fallback. Start from the last decoder read, include the block containing the estimate and cap the extension at **2 MiB**. Fill the first missing interval only. Batch small additions until roughly a quarter of the window is missing, within 64–256 KiB. A request already admitted may finish after pause. |
| Start a recording | Once the first playable PCM is ready, a background worker resolves the immediate successor’s signed URL on either route. A usable URL in the account cache costs zero Graph calls. The current recording can start while Graph is pending. Once the current track has at least three seconds queued, the same low-priority worker begins reading the successor. On either route, early reads may cover the first **256 KiB** (about 6.5 seconds at 320 kbit/s or 16 seconds at 128 kbit/s) and one final block of at most **64 KiB** if the MP3 decoder requests it. A large leading tag can put the first playable packets beyond this allowance. A fenced queue has no trusted Next. One and end-of-track Timer warm manual Next and still stop at EOF. |
| Seek on a metered route | On release, ask Core Audio for a byte estimate using only the first cached 64 KiB. If it cannot supply one, use elapsed time divided by duration times file size. On a miss, request from the block the decoder actually needs through the estimated target block plus 256 KiB of runway. Stop at a cached block, the reserved tail block or 16 MiB per request. Publish complete blocks as they arrive. The first decoded PCM ends the special policy and can cancel an in-flight metered range that overshot by more than the ordinary runway. |
| Decoder asks for the file’s tail during startup | Leave the final aligned block outside the forward window. Fetch it as an independent demand range. This avoids waiting for a multi-megabyte head request to reach EOF. A distant probe while the forward request is active can also use one independent block. |
| Same or adjacent bytes already on the way | A reader waits for the required block on the existing forward response if it has reached that block or is within one block of it. During a metered scrub it waits anywhere within the planned range. It wakes on publication, failure or cancellation. The range also ends at a previously cached block to avoid reading through an already-filled gap. |
| Seek or manually switch tracks | Stop the old reader and drain its task callbacks before the replacement starts issuing requests. Complete blocks remain available. The scrub gesture only commits on release. A fully cached seek and the cached opening of a prepared Next can play with zero new Graph or CDN requests. Decoder and audio-engine startup still take time. A missing block goes directly to the CDN when the account has a usable signed URL. |
| The Wi-Fi window crosses EOF | Expand the successor’s opening allowance when the estimated current bytes remaining fall below 6 MB and PCM is queued. Missing blocks behind the playhead do not affect eligibility. The lower-priority successor reader opens a progressive Wi-Fi-only GET for the first missing part of the prefix. As the playhead moves it can extend the prefix, even after preparing the opening PCM. Ends round down to complete 64 KiB blocks except at EOF. Small extensions to an already covered prefix accumulate to 256 KiB. |
| Preparing a natural join | Decode about 12 seconds of successor PCM. The decoder can consume the Wi-Fi rolling prefix as it arrives and probe the final block separately. On cellular or constrained routes the first missing prefix can be batched into one charged request. Completed blocks are reusable during transfer. A decoder that needs more than the early allowance waits until the join or manual Next. The near-join reads retain their ordinary wire budget. The **4,000,000-byte** speculative wire ceiling covers these narrow attempts, their retries and cancellation, with 2 MiB reserved for cancellation overshoot. If a transfer omits wire metrics, validated blocks remain usable and the occurrence spends its remaining cellular allowance. The rolling prefix is additional traffic allowed only on unmetered Wi-Fi. At promotion the demand reader inherits the URL and any active Wi-Fi-only request with its route restrictions. |
| Repeated preparation | Track charges by queue occurrence across replacement decoders in the same queue. Evicting its cached prefix or seeking in the preceding track does not restore that allowance. An explicit new queue starts a new ledger. |
| Route changes | Consult Network.framework’s current path on each new window. Wi-Fi read-ahead requests explicitly disallow cellular, expensive and constrained access. On a cost/path update, cancel existing Wi-Fi-only reads if the current path no longer qualifies. Preserve completed blocks and fetch still-needed bytes under the new policy. |

The 6 MB window is a read-ahead target. VBR makes the time-to-byte estimate approximate. Decoder probes can fetch bytes outside it, and played bytes remain in the 40 MB pool until eviction. Touching the wheel and spare cache capacity trigger no network work. A manual Next can consume the admitted opening. At a natural join Swift plays the prepared PCM and continues using the same URL. The explicit Debug force-renewal audition requests a fresh URL at the join. These are starting heuristics. A 256 KiB demand read supplies about 11 seconds at 192 kbit/s. The rolling 45-second target extends coverage once playback has started.

## Connections, validation and retries

One ephemeral URLSession supplies the connection pool for the entire player account. Normal completion of a GET leaves the session available for subsequent ranges, seeks and tracks on the same origin. A decoder can issue a tail GET while another response is open. Each request specifies the range and identity content encoding. URLSession manages sockets, TLS and the negotiated protocol. The server, the OS or a route change can retire a connection; OnePlay sends no artificial keepalive traffic. Diagnostics report HTTP status, range, bytes, time to first response, total task time, negotiated protocol and connection reuse. They omit signed URLs.

A response must match the requested offset, end and known object length. A whole-file 200 is allowed only for a matching entire-file request. Readers sharing a signed resource also share its HTTP validator. A strong CDN tag can be sent back to that resource with If-Match. An expired, missing or changed resource (HTTP 401, 403, 404, 410, 412, 416 or a changed validator) can trigger one Graph replacement per demand read. A renewed URL must still refer to the same Graph version and size. A resumed seek can consume cached bytes even while a previous attempt at renewal is waiting. A transient network or service failure retries the same URL with backoff. The shared media session sends neither Graph credentials nor cookies.

Microsoft's driveItem documentation gives a typical lifetime of one hour. Its download documentation says a URL can expire within minutes. The player keeps no expiry timer and responds to the CDN when a missing range is needed. [driveItem resource](https://learn.microsoft.com/en-us/graph/api/resources/driveitem?view=graph-rest-1.0) · [Download behavior](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0)

## Reading the Debug drawer

In the native Debug build, turn on **Settings → Debug** and expand the player. The three bars show the previous, current and next queue entries. Each rail spans the file from byte zero to EOF. A complete offline recording fills the rail in dark blue. For streamed recordings, dark green marks blocks in the compressed cache and black marks gaps. A red glowing interval covers the requested byte range from task start until completion or cancellation. An in-flight range can overlap green as a progressive response delivers blocks. A pulsing red dot at the left edge marks the Graph item metadata download, including its response body. On either route the Next rail can show that dot as the current song starts. Once the current recording has three seconds queued, the next opening can turn green even early in a long track. A 401 replay produces another dot. Token acquisition, drive verification, backoff, and the artificial renewal hold are outside that interval. The white line is elapsed playback time divided by duration. Its alignment with byte offsets is approximate for variable-bitrate MP3s.

Swift samples the cache and live range tasks for the expanded Debug drawer and pushes activity changes to the visible page. Very short requests can finish between display frames. The ordinary clock sample also refreshes streamed coverage. Opening the drawer does not initiate any metadata or audio fetch. Signed URLs and tokens are never part of the display.

### Build 21 cellular seeks and earlier successor lookup

An MP3 frame can be recognized in the middle of a file, but it carries no absolute song timestamp. Variable bitrate breaks a linear time-to-byte mapping, and Layer III frames can refer back to previously encoded bytes. On three recordings from *The Wall*, asking Apple's file decoder to seek to 80% made it visit each intervening 64 KiB block. On “The Thin Ice” that was 9,185 byte callbacks and 47 distinct blocks through the first four seconds of resumed PCM. The callbacks read local blocks whenever available. Build 21 uses the stream parser’s packet estimate and audio-data offset to size the HTTP range. The file decoder still seeks to the requested sample frame. A test using only duration and size needed two GETs at four positions on a track whose first half was encoded at a higher bitrate. Apple’s estimate from the retained header brought those same seeks down to one GET each. [Apple stream seek](https://developer.apple.com/documentation/audiotoolbox/audiofilestreamseek(_:_:_:_:)) · [Apple file seek](https://developer.apple.com/documentation/audiotoolbox/extaudiofileseek(_:_:))

The macOS loopback test used the shipping Swift reader, decoder and metered policy. Each trial started with exactly the blocks retained after decoding the opening four seconds. It opened a fresh decoder, sought to one of 26 positions from 1% to 99%, and counted CDN GETs through the first four seconds of resumed PCM or EOF. Nine files covered the three album recordings, a six-minute CBR track, indexed and unindexed VBR, a 22.05 kHz file, and two sharply uneven VBR encodings. **168 seeks needed one GET and 66 needed zero.** Every output matched the equivalent local-file seek on both channels. Eviction, separate holes, an inaccurate estimate, a scan over 16 MiB, and transport retries can each add requests. The 99% field goal remains unmeasured. The native player uses the same MP3 time-to-byte estimate as the cellular seek window to identify the block at the listener’s target. It checks that block in the versioned cache when opening the decoder. A hit keeps the time visible until the first PCM is queued, including during separate header or seek-scan reads. When Core Audio can only estimate a seek offset, any retained audio for that version keeps the time visible during setup. This can also keep the time visible on a cold seek in a partially cached variable-bitrate file. Core Audio still chooses the exact playback position. A cache miss elsewhere or a successor lookup during audible playback affects only the debug strip. If queued PCM runs out while the required decoder waits for input, the drawer can show the spinner after 250 ms. Once visible, it stays on through later reads and decoding until the node has playable audio again. An accepted seek evaluates its own target, even within the same queue occurrence. An edit that keeps the current target preserves its visible wait.

In the seeded-cache XCTest, a seek to evicted data held the metadata response until the actual screen showed both the spinner and the lookup dot.
