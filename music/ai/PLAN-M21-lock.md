# M21 plan: Recover the library after lock

## Summary

Let an interrupted library startup finish when local data returns. Keep Swift focused on native playback and its existing services. Prove what happens on resume, WebContent replacement and a true process restart, then review the listener experience.

## Problem

On LuPhone13 with native build 71, a listener locked the phone while playing a track in One mode. On return, OnePlay displayed “Could not finish startup. Please reload.” The document logged its launch at 07:50:47.398. The nominal five-second deadline fired at 08:08:10.464, around 17 minutes and 23 seconds later by the wall clock. The same document read a usable 12,057-track cache 275 ms later. It logged “showing cached” even though the deadline prevented the tree from rendering. A subsequent document opened the same cache and showed the library.

On the iPhone 13 Pro simulator, ordinary lock, natural end in One mode, and wake preserved the app and WebKit processes. Forcing WebKit to exit under lock caused OnePlay to start a fresh library document while the native player survived. Forcing a late local cache response in that replacement reproduced the exact screen. The phone's early signed-in evidence favors a WebKit replacement within a live native process. The trigger for that replacement and the reason the local read was deferred remain unknown.

The existing design treats a deadline as a final UI outcome even when startup keeps running. Native playback and the library page have independent lifetimes, so this policy can make a routine replacement of the screen look like a fatal app failure.

## Goals

- On return to OnePlay, show the last valid location in the cached library and the current native playback state. This applies whether WebKit survived, was suspended, or has to be recreated.
- Allow useful local startup work to finish after a delay. Keep background OneDrive work independent of cached browsing, including when connectivity or credentials are unavailable.
- Keep the native boundary small. JavaScript owns library, favorites and browsing state and restores them from WebKit storage. Swift supplies the live background player state it already owns.
- Treat lock, wake and recoverable process loss as ordinary operations. Ask for listener action only when there is a concrete need, with an explanation and an action that addresses it.
- Prove which iOS lifecycle cases the app handles. Record process identity, actual screen and player behavior, deliberate fault injection, and any remaining limitations. Make every user-visible compromise explicit for owner review.

## Prior evidence

Build 71 tests used an iPhone 13 Pro simulator running iOS 27.0, with a synthetic account and two pinned MP3s. An ordinary One-mode end left the same WebKit page usable after another 75 seconds of lock. A forced WebContent exit caused a new document before wake both during playback and after a locked idle interval. A delayed favorites callback reproduced the error while the native playhead advanced. A separate full native process restart restored the saved One-mode position paused. The simulator establishes the failure path. The handset's original operating-system event is still unclassified.

The investigation logs, experimental hook and screenshots are in the local [simulator evidence](/tmp/oneplay-ios-startup.gdOiyL/evidence.md).

## PLAN

### 1. Define the iOS contract

UIKit can suspend a background scene or start the process for a background event. Active playback is an allowed background activity. WebKit has its own process and can tell the native app that the renderer exited. Native scene activation and WebKit document visibility are different observations. A timer may run late, and its delivery order relative to a storage callback makes no claim about that callback's eventual outcome. [UIKit lifecycle](https://developer.apple.com/documentation/uikit/managing-your-app-s-life-cycle) · [Background audio](https://developer.apple.com/documentation/AVFAudio/AVAudioSession/Category-swift.struct/playback) · [WebContent termination](https://developer.apple.com/documentation/webkit/wknavigationdelegate/webviewwebcontentprocessdidterminate%28_%3A%29) · [HTML timers](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#timers)

Keep the current replacement path in [BundledShell.swift](../ios/App/BundledShell.swift) and [LibraryController.swift](../ios/App/LibraryController.swift). A reported WebContent exit retires the old document and creates its replacement with the same account store, even if the app is locked. UIKit activation can reuse an intact page. During replacement, Swift services playback and system controls through Lock Screen or Control Center. The in-app footer returns with the tree and the native snapshot. Cold native restore stays paused at the saved checkpoint.

Background replacement worked when the simulator's local data arrived promptly. Delaying delivery of that same result reproduced the failure. Keep the existing native scheduling and fix the shared startup policy. A native foreground-only creation rule would add coordination across retirement, sign-out and scene activation. Bring the owner evidence if a supported wake test still produces a failed replacement or blank screen. Run the physical checks below for device scheduling and audio. [Apple's simulator guidance](https://developer.apple.com/documentation/xcode/running-your-app-on-simulated-or-physical-devices)

### 2. Replace the terminal timer with one optional recovery affordance

Use [index-startup.ts](../src/index-startup.ts) for opening copy and retry rendering. Await the actual startup promise. Remove the `deadline` terminal, the race against the timer, the guards that reject late tree, index and sign-in renders, and the first-index bypass flag. An active progress screen stops the wait timer. A settled startup still showing opening or progress needs a concrete result. Consolidate the duplicate initial fall-through checks in the startup wrapper. Keep the native interactive sign-in's separately settled check, the service-worker reload wiring and the OAuth exchange's existing network timeout.

Use the existing status region. Show “Opening your library…” initially. After a sustained visible wait, update it to “Still opening your library…” and offer **Try again**. Start with one 15-second threshold for both hosts. The original promise can still finish and present the tree, sign-in or progress. A deliberate tap disables the button and uses the existing document reload path, including native retirement and request cleanup. If the listener retries during a stalled browser OAuth exchange, the original one-use verifier is already consumed. A fresh sign-in may be needed. Reuse the same retry button for a resolved failure. Give it a selector distinct from the sign-in button.

Anchor one timer to the existing opening screen. Arm it when that screen is visible. Cancel it on observed hide or departure from the screen. On observed return, start a fresh interval if the screen is still opening and the action has yet to appear. Leave an already offered action in place. Recheck visibility and opening before publishing, and remove the listener once opening ends. The timer follows what the document observes. UIKit and WebKit can deliver their events at different times, so the optional action may appear sooner than expected after waking. First-index progress follows its existing request and build policy. A short lock can still be followed by a brief opening screen when WebKit needs rebuilding. The app uses one live library view and the existing stores.

### 3. Route concrete startup outcomes to the existing owners

Use [index.ts](../src/index.ts) for account admission and cached rendering. Keep the tree layout-visible during its synchronous setup so breadcrumb measurement and scroll restoration work. Record successful first tree installation only after the tree renders and the controls are wired. Use the existing startup success observation to distinguish an installed tree behind Settings from a partial render that threw. Retire a partial first install through the document retry action. A subsequent pull must respect that failure and leave the retry screen in place. Log “showing cached” only after rendering succeeds. Preserve folder, scroll and the existing fallback for a stale path. Keep native footer attachment through its current snapshot path. A replacement can reset an in-progress search, dialog, drag or expanded native drawer. A surviving page keeps its existing UI.

Route [index-sync.ts](../src/index-sync.ts)'s no-cache failures into the same opening status area. The pull coordinator owns the result whenever it tries to open the first library, including after browser online recovery. If a pull settles after progress without producing a tree or a specific recovery action, present the same failed-opening screen. Reuse the existing pull completion/error path, auth and network evidence, and first-index reporting. Proposed screens for independent UX review and owner approval are below.

| Condition | What the listener sees | What the app does |
| --- | --- | --- |
| Cached library arrives normally or late | Saved folder and scroll, then the current player state as the existing snapshot arrives | Restore immediately from local data. Pull from OneDrive independently when allowed. |
| Opening still pending after a sustained visible wait | “Still opening your library…” with optional **Try again** | Continue the attempt. Any valid result renders automatically. |
| No local library and definite offline evidence | “Connect to the internet, then try again.” with **Try again** | Use this on both a first-ever offline launch and a paired launch with an empty cache. Browser online recovery can open a library or show sign-in through the existing pull. Native empty-library startup needs a retry tap after connectivity returns. |
| No local library and OneDrive requires interaction, without definite offline evidence | Existing **Sign in with OneDrive** action | Preserve browser PKCE and native account pairing. If returned Graph account details conflict with the native pairing, reject them and keep the sign-in action for an empty library. A different account chosen during interactive sign-in keeps the existing “Reconnect with the OneDrive account used for this library.” guidance. |
| Saved native cache is paired to a different drive | Existing “This cached library belongs to a different OneDrive account.” | Keep the cache closed. This existing exceptional screen offers no action. Account repair is a separate owner decision. |
| First library is being built | Existing indexing progress | Continue through the current bounded indexing and transport retries. |
| Opening or first indexing completes with a failure and no usable library | “OnePlay couldn’t open your library.” with **Try again** | Use this for unclassified transport or server failures, unsuccessful Music folder probes, rejected cache reads and unexpected failures. Keep status codes and causes in Logs. A failure after the cached tree is ready leaves browsing usable. Existing sync status can report what failed. |

Treat a rejected primary cache read as a failed opening. Reserve first-time indexing for a confirmed cache miss. The browser's online and visibility pull triggers can run before that determination today. Keep early evidence reconciliation and resume logging, and enable event-driven pulls after local bootstrap has installed a usable tree or confirmed cache absence. Have the existing startup pull read current evidence at that point. A rejected read exposes retry without starting a pull against missing data. Keep the existing favorites/share projection and trust checks, source denials, stale proof fencing and cleanup-pending ordering. Reuse the existing one-document startup, sync single flight, cache formats and bridge.

Use neutral status styling and a single polite announcement when the optional action appears. Keep focus in place. If automatic recovery removes a focused button, hand focus to a stable control on the resulting screen. Provide 44 CSS px tap targets, visible focus and at least 4.5:1 action text contrast in both themes, including the pressed state. Scope any needed CSS to the startup action. [Contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) · [Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
