# M20 plan: Extract the music provider boundary

## Summary

Extract the shared app-document and browser media operations and the concrete OneDrive catalog operations. OneDrive and its shares keep their current login, cached startup, refresh, cloud documents, streaming and offline playback behavior. The refactor is ready when the same legacy files and accounts work on the deployed PWA and the signed iOS build.

## Locked user decisions

- M20 is a provider refactor of OnePlay Music. It establishes the boundary for the existing OneDrive account and its existing OneDrive shares in both the hosted PWA and bundled iOS app.
- The existing OneDrive indexes stay in schema 1, with the same JSON, encoding, filenames, namespace layout, recursive-size reuse and single-page listing policy. Preserve the intentional filename collision between `A/B` and `A_B`. Existing indexes need no migration or rebuild for this milestone.
- Demo music and App Review remain the next product priority. M20 scope ends at behavior parity. Demo data or entry points, additional sign-ins, provider or workspace UI, Google Drive, Dropbox and cross-cloud mirroring belong to later milestones.
- Use [the provider design](../../google-dropbox.md#proposed-in-app-api) as the direction. Prefer extracting demonstrated dependencies over prebuilding multi-account infrastructure. The implementation is a separate step after plan signoff.

## PLAN

### Boundaries and ownership

Keep the current account, source, queue and persistence identities. OneDrive is the only active account grant. A primary library and its shares use that same grant for Graph calls. The existing share record ID still fences a detached and reattached share, even when both records have the same root key or drive and item IDs. The existing `driveId:itemId` byte key still deduplicates offline recordings across authorized aliases. These identities persist in the current files, bridge payloads and database keys.

Add `music/src/provider.ts` for the app-document and browser media contracts. Add `music/src/onedrive-provider.ts` for the OneDrive implementation. Compose it in `index.ts` with the existing browser or native library transport. Give each caller only the method or subset it uses. The browser media calls use the existing drive/item locator, including for an existing share. Account and share bindings still use the existing roots and controllers.

```ts
interface BrowserMedia {
    playbackUrl(driveId: string, itemId: string): Promise<
        Readonly<{ url: string; expiresAt?: number }>
    >;
    download(driveId: string, itemId: string, signal: AbortSignal): Promise<Blob>;
}

interface PrimaryStore {
    read(name: string, signal?: AbortSignal): Promise<string | null>;
    write(name: string, text: string, signal?: AbortSignal): Promise<void>;
}
```

`playbackUrl` supplies an HTML media URL and a conservative absolute expiry in epoch milliseconds. `download` supplies a complete Blob. Fulfill that promise only after reading the body. `null` from `PrimaryStore.read` means the app document is absent. Transport failure and unusable body data remain failures. Callers with no cancellation use the current request lifetime.

The catalog seam in M20 is a live, concrete OneDrive operation that builds from a verified probe and returns existing `MusicData`. The coordinator still consumes its count and cache metadata. The proposed provider-neutral `refreshCatalog(signal): Promise<MusicFolder>` applies to sources that refresh a live index. M20 keeps the existing result so OneDrive can preserve cache reuse, progress and durable publication through its current scheduler. Demo reads a pregenerated tree and has no refresh operation. The first additional source that maintains a live index is the point to extract the shared refresh interface.

### 1. Extract primary document access

Implement Graph app-folder reads and whole-text replacements for the two existing logical names, `favorites.json` and `shares.json`. Use the same endpoints, auth wrapper, retry options, redirects and request body serialization. The app-folder scoped grant already provides this capability in both hosts. Keep schema and reconciliation in `favorites.ts` and `shares.ts`. The store sees serialized document text and never decides which version wins. Sanitize body-read failure in the adapter using the actual status and the current operation label. Sanitize JSON parse failures after reading text at the shared document boundary, retaining the operation label and the Graph document read’s normal success status 200 in its diagnostic. Preserve the diagnostic tests for redaction and parse stage. A successful HTTP 200 with malformed JSON, JSON null, or an invalid document shape keeps the current load-failure path. Only an actual 404 marks the remote membership as known and absent. Preserve the current HTTP failure status and diagnostic labels when a request fails. [Microsoft app-folder access](https://learn.microsoft.com/en-us/graph/onedrive-sharepoint-appfolder)

Wire the existing whole-document pull and save paths to `PrimaryStore` and keep each module's local transaction and coalesced upload loop. Keep favorites playback fences, mode/pin-only change callbacks, the server timestamp comparison, share normalization, and the in-flight share pull guard. Transfer the favorites test-only save suppression to the new dependencies. While the hook is active, new local and remote writes remain suppressed and new remote pulls return false without adopting data or qualifying for healing. An operation already dispatched retains its current lifetime. Move share URL encoding, Graph redemption and whole-drive Music folder resolution into concrete OneDrive methods. Keep the split that the current share-add flow needs. First return the share ID and encoded token, using the token as the ID fallback when Graph has no usable ID. The caller checks for a duplicate, then captures the native source-proof ticket for the resulting root key. Only then resolve the folder and return its current locator, display name, and original proof response from the final request. Keep the published share record, explicit disconnect, and admission decision with `shares.ts`, along with the vendor-authored error messages and URL redaction. The primary document store also stays out of per-folder index cache reads, writes and deletion, which use the Graph batch transport and its own cache namespace.

### 2. Extract catalog I/O and retain the scheduler

Move the Graph calls for account details, Music folder and share-root probes, and share index-cache directory deletion behind concrete methods on the OneDrive adapter. These are concrete OneDrive setup and cleanup operations. Keep the exact `cache: 'no-store'` probes. Return the original native response for a share probe through the existing `beginSourceProbe` path so status, the account proof and account-error headers still affect the same decision. Keep account verification and sign-in evidence with the existing account and orchestration code. A native drive mismatch still fences writes and document publication.

Move the existing indexer invocation behind one `buildAndCacheIndex` method on the OneDrive adapter. It takes the verified OneDrive folder metadata, drive ID, current namespace, progress callback and optional abort signal. It calls the existing `buildIndex` with the same Graph transport and native content-follow callback. Its sole result is the existing complete `MusicData`. The same method serves the primary and share builds.

Keep the cache hit and build-start decisions in `index-sync.ts`. A hit reuses the existing snapshot with zero index-cache writes. It still marks the folder current and updates the primary last-checked timestamp. A miss enters the current progress path, including the first-time startup deadline exception, before awaiting the adapter. Keep the existing durable commit before publication, with the same checks before and after a share save. Keep cancellation, active-build tracking and share reconnect identity together in the coordinator. It still owns cached publication, retry/evidence gating and single-flight scheduling. It needs no catalog-specific callback to receive a second snapshot or another job token.

Preserve refresh order. Start the favorites pull, await the share document pull, load and publish cached shares, then run the Music and share probes concurrently. End the short checking indicator after the probes. Build primary first, then shares sequentially. With a cached tree already visible, a failed primary Music probe leaves a healthy share eligible. Initial startup with no tree still uses the existing primary failure path. For disconnect, withdraw playback access, cancel and await the dispatched share build including any Graph or local write, then delete that share's cached index. A replacement connection can appear while cleanup settles. Cache loading skips the old namespace during deletion. The sequential refresh waits for that deletion before using a probe or cached snapshot for the replacement. Pass only roots verified current or rebuilt and committed to favorites healing after both remote pulls have qualified.

Keep `indexer.ts`'s work queue, request grouping and retries intact. The Graph paths use `primary/` and `share-${encodeURIComponent(shareId)}/`, with `index.json` at the root and the current underscore-joined subtree filenames. IndexedDB keeps `index:<driveId>` and `index-share:<shareId>`. Keep the existing base64-as-text upload encoding and schema/recursive-size check. Batch cache redirects continue to use the transport that admitted the batch, including native content-follow. The browser transport retains its direct CDN behavior. The old app and the refactored app must be able to read one another's indexes. [Original cache rules](PLAN-M3.md#learnings-from-example-code) · [Graph content routes and ranges](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0)

### 3. Extract browser media access at the existing call sites

The browser playback URL engine and downloader currently issue the same Graph item metadata request. Put that lookup in a private OneDrive adapter function. Pass the existing drive and item IDs directly to the methods. Preserve each caller's current timeout, cancellation and retry options. Keep the signed content request separate from authenticated Graph metadata. The adapter computes the existing expiry for playback URLs using the same maximum lifetime, fallback and parsed expiry. `PlaybackUrlEngine` retains the synchronous cache-hit path, prefetch, expiry refresh threshold, invalidation, and Blob URL lifetime. A prepared next track can still advance without waiting on an async binding or network call. Treat the adapter call as one in-flight lookup, through metadata body decoding. Compare the existing lookup counter after the call settles before publishing or clearing the ready entry. Successful metadata without a URL invalidates any ready URL for that item. HTTP or body-read failure leaves a still-valid ready URL usable.

The browser adapter reads the full response into a Blob for offline use. Carry every unsuccessful metadata and CDN response status to the existing worker through one small status-bearing error, including synthetic statuses returned by `auth.fetch`. Give successful metadata without a URL a recognizable unavailable error. Preserve the original signal and body/network failure behavior. The worker continues to apply its own status and evidence rules to these failures. In particular an absent media URL is unavailable, 404 finishes work for that recording, throttling or retryable service failures requeue, and auth or timeout still affect evidence as before. Keep body-read errors, intentional cancellation, and network/timeout failures distinct. The download queue still owns retry and generation policy, pending IDB saves, quota, retention and offline playability. A stale result cannot publish inventory through a retired queue. Keep Blob storage and key derivation in the downloader.

### 4. Keep native ownership and ship the shell on both hosts

The native player and pin service already receive injected media lookup closures in `LibraryController.swift` and use `NativeAccount.media` for the active OneDrive binding. These are the Swift side of M20's boundary. Keep them as the two existing call sites, including the playback hints and the pin retry hints. App playback remains native with WebKit absent or suspended. No native queue, manifest, pin ticket, bridge protocol or cache key migration is needed. Keep the signed URL result, all current native request/renewal behavior and the account-owned URLSession. Qualified native lookup for independently authenticated sources belongs with the first such source. Deriving a unique source from the current deduplicated pin byte key would change the meaning of overlapping owners.

Include the OneDrive adapter and the provider module containing the shared error code in `sw.js`'s shell closure and `ios/ShellInputs.xcfilelist`. Use the existing counter and packaging flows. Shared TypeScript must reach the hosted PWA and bundled WebKit. Update [architecture notes](ARCHITECTURE.md) at implementation time with app-level ownership that actually changed. The compatibility contract comes from the current [native account](../ios/App/NativeAccount.swift), [player and pin wiring](../ios/App/LibraryController.swift), and [shell packager](../ios/package-shell.sh).

## BETTER ENGINEERING INSIGHTS + BACKLOG ADDITIONS

- An app document store and a per-folder Graph index cache have different responsibilities. The existing optimized batch pairs a listing and cache I/O under the same bearer. Extracting the primary document store removes Graph from core favorites document operations without turning that optimization into a generic storage API.
- OneDrive's media resolution can be shared across browser playback and downloads. Prefetch and queue policy belong to their existing callers. Swift already owns those scheduling and transport boundaries.
- Demo can load its pregenerated bundle catalog into a local-only workspace after M20. A later differential-grant source needs explicit source routing, per-source evidence, source-scoped cache admission and a persistence policy. A catalog mirror in the primary must never prove current item access by itself. The approved OneDrive layout can coexist with separate new-provider catalog documents. [Provider design and release gates](../../google-dropbox.md#does-the-api-fit)
- **Planning evidence.** The baseline TypeScript build and all 177 existing web unit tests passed. A local probe of the compiled indexer sent the existing one-page request and cache read for primary and share namespaces. A mocked Graph batch 302 through the injected follow yielded the old Unicode schema-1 snapshot unchanged in both cases. That supports reuse of the existing indexer and transport rather than importing or converting its cache. This probe used fixture responses. Real OneDrive compatibility and the signed builds are implementation checks.
- **Plan review.** Four independent GPT-6.2 Sol High KISS rounds reviewed successive revisions. The first kept a single catalog result and the existing Swift lookup. The second clarified share reconnect ordering, cache-hit writes and test-only save suppression. The third preserved synthetic response statuses and the two playback renewal outcomes. The fourth reviewed the final plan and requested no changes.

## USER VALIDATION SUGGESTIONS
