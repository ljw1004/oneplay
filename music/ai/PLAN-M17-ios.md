# M17 — OnePlay Music on iOS

Build an iPhone app under `music/ios/` that bundles OnePlay’s existing HTML, CSS, and compiled TypeScript in a `WKWebView`. Keep one library UI for the browser and iPhone. On iPhone, pressing Play hands Swift everything needed to play the session. The listener can lock the phone at track one, reach track ten, and reopen the library to find the correct row, footer, scrubber, and saved position.

**Start with the listening test.** Use the listener’s own CD-ripped MP3s. The known boundary is *Sgt. Pepper’s Lonely Hearts Club Band (Reprise)* into *A Day in the Life*. Use *The Wall* for several natural transitions, identifying continuous boundaries by listening to the local files first. Success on cellular means the transition sounds like a gapless-capable player playing those exact files locally. Honor encoder delay/padding information where present, preserve silence in the source, and leave crossfade and silence trimming off.

## 1. Prove playback and sign-in on a physical iPhone

Do this before restructuring the web player or porting the download manager. Build a small, signed Swift target in Xcode. Use a short list of real drive and item IDs, a minimal test screen, and two complete files staged in app storage for the offline test. Start the day-two sign-in check on the first day.

1. Add the iOS/macOS platform and the signed target’s bundle ID to **OnePlay’s existing Entra app registration**. Keep the existing consumer authority and Graph permissions (`Files.Read`, `Files.ReadWrite.AppFolder`). Configure the native redirect URL, callback handling and MSAL Keychain access group. Sign in via the system authentication session. Confirm the account can read its existing favorites, shares and index in the same OneDrive app folder. [MSAL redirect setup](https://learn.microsoft.com/en-us/entra/identity-platform/redirect-uris-ios) · [MSAL token acquisition](https://learn.microsoft.com/en-us/entra/msal/objc/acquire-tokens)
2. Configure a playback `AVAudioSession` and the background audio capability. Give Swift the full logical queue. Start with an `AVQueuePlayer` containing only the current item and its expected successor. Obtain fresh OneDrive download URLs as entries approach playback. Install lock-screen play, pause and skip commands early enough to exercise them in this test. [Apple background playback](https://developer.apple.com/documentation/avfoundation/configuring-your-app-for-media-playback) · [AVQueuePlayer](https://developer.apple.com/documentation/avfoundation/avqueueplayer)
3. Compare the reference transition with local playback through the native engine, then with streaming from OneDrive over cellular, Wi-Fi off, screen locked, debugger detached. Listen to the output. Record the iPhone/iOS version, file pair, route, and whether a discontinuity is audible in each run. Player callbacks alone cannot measure an audible gap. For an ambiguous result, compare captured output around the join with the local reference.
4. Prove **audio bytes for the successor arrive before the boundary**. Measure bytes fetched before transition, time to first playable data, and stalls. Repeat with an unpinned multi-hour file next in line, then skip away from it. Try AVFoundation’s preferred forward-buffer duration first. It expresses a preference in seconds. Measure actual traffic to establish and record a bounded preload budget, and verify obsolete preparation stops. If the player overfetches, implement a bounded range reader whose cached bytes feed the player. Handle a server returning a full response to a range request by stopping speculative reads at the budget. If local playback itself introduces a gap, resolve native decoding or scheduling before tuning the network. [Apple buffering semantics](https://developer.apple.com/documentation/avfoundation/avplayeritem/preferredforwardbufferduration) · [Graph partial downloads](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0)
5. Lock and skip past the prepared item. Record a **fresh Graph URL lookup and successful playback under lock**, then repeat across an access-token renewal. Exercise reading the MSAL cache, local files and bookmarks under device lock after first unlock. Play both staged files consecutively in airplane mode. Interrupt with a call, disconnect headphones, and check the position after returning. More than 24 hours after sign-in, refresh the library while staying on the same screen. Use the prototype’s visible Graph refresh for the early check and repeat in the real library in phase 5. [Microsoft refresh-token lifetimes](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)

Proceed to the shared refactor when the on-device results establish the playback approach. Keep the working native code as the start of the shipping player. Record any failed boundary, excess transfer, or locked-device renewal failure against the corresponding test before expanding its scope.

## 2. Extract the playback boundary with the PWA as its first caller

| Current code | Refactoring work |
| --- | --- |
| [tracks.ts](../src/tracks.ts) and [favorites.ts](../src/favorites.ts) | Produce one ordered queue description from a folder, tapped track, shortcut, or nested playlist. Reuse the existing traversal order, shared-root resolution and denied-root filtering. Include the playback folder, starting occurrence, favorite/resume policy, mode and timer setting. Give each entry its logical path, occurrence identity, physical drive and item IDs, and resolved display labels for the footer and Now Playing. |
| [playback.ts](../src/playback.ts) and [playback-engine.ts](../src/playback-engine.ts) | Keep the facade used by the tree. Move HTML audio events, URL/blob preparation, browser Media Session and browser bookmark storage behind the browser player. Expose session operations for starting/updating a queue, play, pause, next, previous, seek, mode and timer. Reuse the current policy tests for both implementations, including the distinction between natural end and manual Next. |
| [playback-ui.ts](../src/playback-ui.ts) | Remove direct reads of `src`, `duration`, `paused`, and `currentTime`, and direct calls to the audio element on scrub release. Render player snapshots and emit commands. Keep the wheel gesture, skip intervals, near-end pause, and expansion behavior. Drive row indicators and the footer from the same player state. |
| [index.ts](../src/index.ts), [index-startup.ts](../src/index-startup.ts), [index-sync.ts](../src/index-sync.ts) and [auth.ts](../src/auth.ts) | Choose the browser or iOS implementation once during startup. Isolate browser redirect handling, redirect cooldowns, the DOM audio check, token debugging, service worker registration and browser playback restore. Keep shared indexing, evidence handling, favorites, settings and cached-library rendering behind their existing interfaces. |

**Queue identity matters during edits.** A logical path such as `m:3` identifies a row in the current revision. Removing an earlier member can change which song occupies that row. Derive a stable occurrence key from the chain of playlist member identities already used for deduplication, the source root where needed, and the leaf drive/item. Two routes to the same MP3 have distinct occurrences and share one audio file. Test this derivation on nested favorites, overlapping folders and existing saved data. Keep the current logical path alongside the key for navigation. Retain the browser’s existing localStorage and legacy IndexedDB bookmark reads.

**An edit updates the active queue.** On a favorites or roots change, rebuild the affected queue and apply the new revision atomically. Keep a surviving current occurrence playing at its exact position and update its row path. Replace a prepared successor if the edit changes what follows. Characterize current PWA behavior in tests for removal of the playing occurrence, deletion of its favorite, and shuffle refresh before porting those cases. An old row index must never relabel audible audio as a different song. Race the edit against a native advance in the tests.

Build and compare queues in linear passes over the tracks and their path segments. In particular, replace the nested membership scan in `reduceRefreshedTrackList` when checking a 30,000-track shuffle. Measure queue construction, transfer, main-thread stalls, and time to first play on device. Yield during large builds and stage transfers in chunks if needed. The player commits a complete revision and can discard a superseded build. Routine position updates carry only the current entry’s state.

## 3. Connect the bundled web UI to the native session

Have the Xcode build compile and package the same shell assets and ES modules as the web build. Give the bundled page a stable origin and persistent WebKit data store. Verify module loading, IndexedDB, localStorage and an offline relaunch across an app update. Use the bundle as the iOS shell. Keep the PWA’s service-worker shell list in step with any TypeScript modules introduced by the refactor.

| Direction | Contract |
| --- | --- |
| Web UI → Swift | Start a session or revise its ordered queue, send transport/mode/timer commands, and request the latest snapshot on attachment or return to foreground. Qualify revisions, seeks and asynchronous replies with the applicable session and occurrence so obsolete work can be discarded. |
| Swift → visible web UI | Publish actual track, logical path, loading/playing/paused/stalled/error state, mode, duration when known, position and rate. Report a track change, seek, stall, resume, pause or interruption immediately. Start with a position sample about once per second while playing. Use an increasing sequence number so late replies cannot rewind the display. |
| Scrubber | Between samples, advance from the last reported position using elapsed time on the web view’s monotonic clock. Freeze on pause or stall. While dragging, display the finger’s position. Commit one seek on release for the occurrence that was touched. Reject a stale seek if a headset skip or automatic advance changed tracks during the gesture. |
| Background and restore | Detaching or destroying the web view ends the subscription. Swift continues queue advancement, URL renewal, buffering, controls, timer and bookmark saves independently. A returning view subscribes and takes a current snapshot before rendering or sending restored state. After a full process restart, restore the durable session paused and start audio on an explicit Play. |

Implement one native session that handles both UI commands and `MPRemoteCommandCenter`. Publish title, album, elapsed time, duration and rate to `MPNowPlayingInfoCenter`. Map interruptions and route changes to real player state, pause on headphone disconnect, and respect the listener’s pause intent when an interruption ends. Cover All, Repeat, Shuffle, One, and Timer, including end-of-track sleep, timed expiry in place, and reshuffle without immediate repetition. Preserve the existing rule that a playback error stops on the affected track. [Apple remote commands](https://developer.apple.com/documentation/mediaplayer/mpremotecommandcenter)

Persist queue/order and mode at structural changes, and save small position checkpoints periodically and on pause, seek, interruption and track change. Persist global and per-favorite local positions in Swift for the native app. The favorite’s configured mode still syncs via TypeScript and `favorites.json`. Reconcile that setting on attachment without sending an old bookmark back over a live session.

## 4. Route library requests and offline audio to their owners

**Authentication.** Use the same native MSAL account for playback, pinning and foreground library requests. Keep credentials in the native token cache. Adapt the existing `AuthFetch` interface over the bridge for trusted Graph requests from the bundled main frame. Preserve methods, request bodies, response status/headers, cancellation, timeouts, the caller’s throttling/retry policy, and `cache: 'no-store'` for recursive size probes. Exercise a real index batch including its preauthenticated redirect follow, a favorite write and a shared-drive read. Keep Graph authorization on the Graph origin. Audio bytes travel directly between native storage, the player and OneDrive.

Try silent acquisition first and coalesce concurrent renewal. When Microsoft requires interaction, keep cached playback and browsing usable, expose Reconnect, and present the system sheet from the foreground. Complete or cancel it in place, preserving selection, scroll and playback. Guard background callbacks by account/session. Explicit sign-out stops playback, cancels transfers and clears that account’s files, bookmarks, credentials and web caches before another account becomes active.

**Downloads.** Keep pin intent and the computation of active/retained `driveId:itemId` sets in TypeScript. Implement the iOS side of the [downloads.ts](../src/downloads.ts) contract with native files accessible while the device is locked. Stream into temporary files and atomically publish complete recordings. Deduplicate overlaps, protect files in active use and reconcile interrupted transfers on launch. Preserve paused favorites, quota, retry/evidence behavior, and the existing offline modal’s counts, bytes and status. Publish compact change events while the UI is visible and a fresh inventory on reconnect. Only complete pinned files qualify as available offline. The transient streaming buffer has a separate lifetime and budget.

On first native launch, recover cloud-backed favorites, shares and indexes from the existing app folder. Treat the iOS install as a new local store. Rebuild its pins from synced intent and establish device-local listening positions. Test the upgrade of an existing PWA separately to preserve its downloaded blobs and saved positions.

## 5. Acceptance and rollout

- **Browser regression.** Exercise the extracted player with the existing TypeScript unit and Playwright suites. Add shared input/expected-result fixtures for duplicate occurrences, live edits, stale seeks, shuffle, timers and favorite resume, and run those cases in Swift tests as well. For the web changes, follow the repository’s build, deploy and integration workflow on localhost and production, including a mobile viewport, offline cold launch and screenshots. Integration progress is written to `/tmp/oneplay-music-test.log`. [Repository test and deploy instructions](../../AGENTS.md)
- **Native independence.** On a physical phone, destroy the web view after Play, lock it, advance past the prepared window, let it reach track ten, and use headset or lock-screen controls. Recreate the view and verify row, title, time, mode and bookmark. Repeat offline with real pinned tracks, an interruption, headphone disconnect and a sleep timer. Verify a cold restart restores the last saved position.
- **Live edits and scrubbing.** With A playing and B buffered, remove B so C is next. Hear A run into C after lock. Repeat with a shift in the current row’s index, two occurrences of one recording, and a remote skip during a scrub. Check that a background-to-foreground transition never replaces a newer native session with stale web state.
- **Listening and transfer.** Repeat the *Sgt. Pepper* pair and identified *The Wall* boundaries on cellular with the shipping bridge and player. Record the reference comparison, successor bytes loaded before each transition, and the large-file preload measurement. Also exercise a network loss, an expired URL and a recovery. Separate a genuine network stall from a reproducible gap with data already buffered.
- **Sign-in and scale.** On day two, refresh an existing library from its current folder and confirm the page stays in place. Exercise required interaction, cancellation, reconnect, then explicit sign-out. Measure cold cached launch, first-play latency and queue handoff for a 30,000-track library. Verify an edit during a large transfer leaves one coherent playing session.

The milestone is complete when the browser regression checks pass and the physical iPhone reproduces the reference transitions, advances independently under lock, respects the measured preload budget, and reconnects to OneDrive without a library reload. Record actual device results and the chosen buffer settings in this plan when implementation reaches those gates.
